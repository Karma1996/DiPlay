2. 背景与问题陈述

人类原话（唯一需求来源）：「第一次链接之后，后续链接不在需要手动进行链接，而是可以支持自动链接设备。」

DiPlay 当前的无线 CarPlay 通路已经具备四种网络后端：MANUAL_HOTSPOT（内置车机热点，推荐）、WIFI_P2P（Wi-Fi Direct）、LOCAL_ONLY_HOTSPOT、EXISTING_WIFI（同一外部 Wi-Fi）。每一次无线会话的建立都走：准备网络 → 通过蓝牙 RFCOMM/iAP2 向 iPhone 发送 Wi-Fi 配置（0x5703）→ iPhone 加入热点 → 首包 TCP（30 s 超时）→ 认证 → 投屏。

问题不在「能不能连」，而在「每一次都要人推一把」：车机上电后要打开 DiPlay、点「Connect phone」；车机热点常常需要先到车机设置里打开；而现有的自动化开关分散、默认关闭，且部分依赖 ADB 授权，普通车主实际上拿不到。

2.2 差距分析

把「后续不用手动」拆成一次都不用点，当前链路有 6 处断点：

  1. 入口断点：没有开机自启（或浮窗权限缺失）时，车主仍要手动点开 DiPlay；点开后又因为 auto_connect 默认关闭而停在 Home。
  2. 网络断点：车机热点未开时，连接被 carHotspotOffDialog() 拦下；自动开热点依赖 ADB，未授权用户只能去车机设置手动开。
  3. 触发断点：休眠唤醒（非重启）没有任何自动触发；iPhone 重新回到车内时，只有开关打开且接收器存活才会唤醒。
  4. 失败断点：自动尝试失败后回到手动状态，没有「等 iPhone 到达再试」的有界策略，也没有统一的失败原因与一键恢复入口。
  5. 策略断点：首次配对与后续重连没有产品级的差异化定义——首次要选设备、要确认；后续不应再出现选择界面，但当前多设备场景仍会抛出需要人工介入的失败。
  6. 默认值断点：所有自动化开关默认关闭且分散，车主不读文档就不会打开，于是「支持自动连接」在默认体验上等于不存在。
本需求不是从零造功能 现有自动化能力（打开即连、蓝牙唤醒、开机自启、自动开热点）是本需求的基础，需求要做的是：把它们收敛成一个默认可用、无需 ADB 也能成立、失败可回退的统一策略，并补齐休眠唤醒与失败恢复两处空缺。任何"推倒重做连接栈"的方案都不在范围内。

3. 目标、成功度量与非目标

3.1 目标

  • G-1：首次无线连接成功之后，在车机上电、DiPlay 启动、首选 iPhone 蓝牙到达、休眠唤醒这四类触发下，车主不需要在车机屏幕上做任何选择或点按即可进入 CarPlay。
  • G-2：自动连接失败时，车主能在一次操作内恢复（重试、或按提示打开车机热点），且不会被无限重试或阻塞弹窗困住。
  • G-3：自动连接不降低既有安全边界：不自动信任新设备、不跳过 iAP2 认证、不新增凭据外泄面。
  • G-4：在无 ADB 授权的普通 DiLink 车机上，至少保证"打开 DiPlay 即自动连接"这一档可用（降级阶梯，见 FR-002）。

3.3 非目标（明确不做）

  • NG-1 不改 USB / 有线 CarPlay 的自动连接与重试行为（FR-014 只要求不回归）。
  • NG-2 不新增配对方式：仍要求 iPhone 与车机先完成蓝牙配对；不做二维码配对、不做 BLE 靠近（RSSI）自动发现。
  • NG-3 不改 iAP2 / MFi 认证、不动 accessory 身份资产、不改发布签名。
  • NG-4 不支持非 BYD 品牌；不改动 Geely / 其他厂商的既有兼容分支。
  • NG-5 不重新设计连接栈，不替换 4 种网络后端，不引入新的热点实现。
  • NG-6 不改变车机热点口令的存储介质（仍为应用私有 SharedPreferences；见 NFR-004）。
  • NG-7 不做"人离开自动断开"的接近检测。

5. 功能需求 FR

全部 FR 的来源只会是三类：人类原话、仓库/文档事实、已记录假设（A-xxx）。优先级：P0 = H1 必须接受且首发必须实现；P1 = 首发应实现；P2 = 可延后但需记录。

FR-001 首选设备记忆 P0

描述
首次无线 CarPlay 连接成功后，系统必须把该 iPhone 记为「首选设备」，并至少保存：蓝牙地址、显示名、连接方式（MANUAL / WIFI_P2P / EXISTING_WIFI）、最近一次成功连接时间。后续所有自动会话只以首选设备为目标。
输入
首次成功会话（认证完成且投屏渲染）
输出
持久化的首选设备记录，重启后仍存在
边界
只保存一台首选设备；更换设备必须走显式的"Choose iPhone"；不因自动连接而改写首选设备
依赖
现有 phone_address / phone_name 存储
来源
人类原话 + 假设 A-001

FR-002 自动连接触发源与降级阶梯 P0

描述
启用自动连接后，系统必须在以下事件之一发生时自动发起无线会话：
(a) 车机上电且 DiPlay 启动（含开机自启、Launcher 启动）；
(b) 已保存首选 iPhone 的蓝牙链路在车机侧建立（ACL 连接，任意时刻）；
(c) 车机从休眠唤醒且 DiPlay 进程仍在；
(d) 车主打开 DiPlay（最后兜底，任何权限状态下都必须可用）。
降级阶梯：无 ADB / 无浮窗权限时允许 (a) 不可用，但 (b)(d) 必须成立；任何一档成立即视为满足本 FR。
输入
触发事件 + 首选设备 + 自动连接开关状态
输出
一次自动连接会话（或按 FR-007 进入待手动状态）
边界
仅在无线模式生效；默认连接方式为 USB 时不发起无线自动会话；不包含 BLE 靠近检测（NG-2）
依赖
FR-001、FR-013；BootReceiver、PhoneBluetoothReceiver、Activity 启动路径
来源
人类原话 + 差距分析 §2.2 + 假设 A-004

FR-003 自动会话免交互 P0

描述
自动会话期间，不得要求车主：选择 iPhone、输入/确认热点凭据、点按"Connect phone"、确认网络切换。系统权限对话框（蓝牙、通知、USB 等）不在此列，但必须仅在首次需要时出现。
输入
自动触发
输出
无中断的会话建立，或按 FR-007 的失败状态
边界
首次配对场景（S-01）不受本 FR 约束，允许也必须显式选择
依赖
FR-002、FR-004
来源
人类原话「不需要手动进行连接」

FR-004 首次配对与后续重连的差异化 P0

描述
首次配对（从未有首选设备）必须显式：车主选择 iPhone、确认保存热点凭据、接受系统配对提示。后续重连必须不重复上述任何一步，且不得再次弹出设备选择列表。若首选设备记录失效（取消配对/地址变化），必须进入"需要重新选择"的显式状态，而不是自动改选其他设备。
输入
首选设备存在性 + 蓝牙绑定状态
输出
两条互斥的代码/产品路径：首次设置 vs 自动重连
边界
「首次」以是否存在首选设备为准，不以"是否安装过"为准
依赖
FR-001；现有 choosePhone() 与 CHOSEN_IPHONE_NOT_PAIRED
来源
人类原话 + 差距分析 §2.2(5)

FR-005 网络链路准备与自动开启热点 P0

描述
自动会话必须按已保存的连接方式准备网络：
(a) MANUAL：车机热点已开则直接附着；未开且本机具备授权与固件能力则自动开启，并等待热点进入可用状态；
(b) WIFI_P2P：按既有流程建立组，不因自动连接改变信道策略；
(c) EXISTING_WIFI：附着到已保存的外部网络，不创建热点；
(d) 任何后端在无法满足前置条件时，必须停止并给出该后端专属的原因。
输入
首选设备 + 连接方式 + 热点状态 + 权限状态
输出
可用的热点/网络接口与凭据，或分类失败
边界
不新增热点实现；不改变信道自动选择算法；不要求车机联网套餐
依赖
CarHotspotSettings、CarHotspotSetup、四种 WirelessHotspotManager
来源
代码事实 + 差距分析 §2.2(2)

FR-006 有界重试与退避 P0

描述
自动会话对可重试失败必须重试，但有界：单次自动会话最多 5 次尝试、总时长不超过 150 s；两次尝试之间必须退避（不得紧循环）。不可重试失败（如热点配置错误、蓝牙不可用、Wi-Fi Direct 与热点冲突且车主拒绝）必须立即停止，不消耗预算。
输入
失败分类
输出
继续尝试 / 立即转 FR-007
边界
预算按"自动会话"计，不跨会话累计；既有 MAX_STARTUP_RETRIES=5 与 60 s 稳定判定为设计参考，不直接等同于本预算
依赖
WirelessStartupFailure.retryable、WirelessStartupPolicy
来源
假设 A-003 + 代码事实

FR-007 失败停止与手动回退 P0

描述
自动会话结束（成功、预算耗尽或不可重试失败）后必须进入明确状态：保留首选设备与全部设置；在 Home / CarPlay 启动界面显示失败原因与单一"重试"入口；不得自动重开无限会话，不得以全屏阻塞对话框掩盖界面。
输入
FR-006 的结论
输出
「待手动重试」状态 + 可操作入口
边界
失败状态在下次触发（重新上电/蓝牙到达/打开应用）时允许重新开始一次新会话
依赖
FR-010、ConnectionFailureGuidance
来源
差距分析 §2.2(4)

FR-008 多设备与已配对设备冲突 P0

描述
(a) 首选设备可用时，其他任何设备的连接都不得中断或抢占会话；
(b) 首选设备不可用且存在 ≥ 2 台已配对/已连接 iPhone 时，自动会话必须停止并进入"请选择 iPhone"状态，不得静默选择任何一台；
(c) 首选设备不可用且只有 1 台候选时，是否允许自动改连由 A-006 的假设决定，默认不允许，必须显式提示。
输入
绑定列表 + 连接状态 + 首选地址
输出
继续 / 停止并提示
边界
不改变现有"多台已连接时报 IPHONE_NOT_CHOSEN"的判定语义，只改变自动场景下的呈现与恢复方式
依赖
CarPlayController.kt:2615-2662
来源
代码事实 + 假设 A-006

FR-009 断电重启与休眠唤醒 P1

描述
(a) 冷启动（断电重启）按 FR-002(a)/(d) 处理；
(b) 休眠唤醒（未重启、进程仍在）后，若首选 iPhone 可达，必须在唤醒后自动恢复会话，不要求车主点开应用；
(c) 若进程已被系统回收，退化为 FR-002(d)，并在下一次启动时自动连接；
(d) 唤醒恢复不得依赖 CarPlay Activity 处于前台。
输入
系统唤醒事件 / 进程存活状态
输出
自动恢复或按 FR-007 停止

6. 非功能需求 NFR

NFR-001 连接时延 P1

冷启动场景，从上电到 CarPlay 首帧：P50 ≤ 25 s，P90 ≤ 40 s（含热点就绪 ≤ 15 s 与首包 TCP ≤ 30 s 的既有常量）。休眠唤醒恢复：P90 ≤ 20 s。测量点必须写进诊断时间线，不能靠观感。

NFR-002 重试预算与资源占用 P0

单次自动会话：≤ 5 次尝试、总时长 ≤ 150 s；尝试间退避 ≥ 2 s 且逐次递增。预算耗尽后必须停止（FR-006/FR-007），不得以"后台继续尝试"方式延长。

NFR-003 空闲功耗与唤醒频率 P1

自动连接空闲时，DiPlay 自身的轮询/唤醒频率 ≤ 每分钟 1 次；空闲 2 h 的额外 CPU 时间与唤醒次数必须可测量（诊断或 dumpsys 证据）。事件驱动（广播、蓝牙、系统回调）优先于轮询。

NFR-004 凭据与隐私 P0

车机热点 SSID/口令仅存于应用私有 SharedPreferences（xcertplay_airplay，MODE_PRIVATE）；allowBackup=false，不进入系统备份；不进设置备份文件（SettingsBackupCodec 白名单不含）；不进诊断报告（DiagnosticRedactor 拦截 ssid/passphrase 行）；不出设备、不上传。自动连接不得新增任何凭据副本。

NFR-005 认证不降级 P0

自动连接必须完成既有的 iAP2 / MFi 认证流程；不得为缩短时延跳过认证、放宽信任判定或接受未配对设备。任何"快速重连"优化都必须仍然验证对端身份。

NFR-006 兼容性 P0

Android 7.0（API 24）及以上；BYD DiLink 3.0 / 4.0 / 5.x 为承诺范围；4 种网络后端在各自适用车型上不得因本需求回归。非 BYD 品牌不作承诺（NG-4）。

NFR-007 可维护性与多语言 P0

新增/修改的每个字符串必须补齐 11 套 values*（默认 + ar/es/it/ja/ko/ru/tr/uk/zh-rCN/zh-rTW）；阿拉伯语通过 RTL 校验；设置项落到唯一 SettingsCategory；SettingsLayoutPolicyTest、AdaptiveSettingsUiTest、SettingsTranslationsTest 不得靠改测试通过。

NFR-008 稳定性 P1

100 次冷启动/唤醒循环中：无 ANR、无崩溃、无重复会话、无线程/连接泄漏；单测覆盖超时、断流、重连、边界长度等分支（项目约章 §5.7）。

NFR-009 可观测性 P1

诊断报告必须能回答：哪个触发源、哪个后端、卡在哪个阶段、尝试次数、总耗时、失败分类。字段固定、可 grep；不得包含 SSID、口令、MAC、IP、配对记录。

NFR-010 无障碍 P2

自动连接状态与开关必须可被 TalkBack 朗读（含 checked 状态与失败原因）；键盘/方向键可到达；大字体与 RTL 下不截断、不遮挡。

NFR-011 驾驶安全与界面礼貌 P1

自动连接不得以全屏阻塞对话框抢占界面；不得覆盖倒车影像等系统级界面；失败提示允许延后展示或忽略。任何自动弹出的界面必须可被车主一键关闭。

8. 业务规则、权限、数据与隐私

8.1 业务规则

  • BR-1 一台车机同时只有一个首选设备；更换必须显式操作。
  • BR-2 自动连接永远不选择"非首选且非唯一候选"的设备。
  • BR-3 自动连接失败不得改变车主任何已保存设置（设备、热点、模式）。
  • BR-4 有线优先原则不变：USB 插入时按既有逻辑处理，不被无线自动会话抢占。
  • BR-5 首次配对必须由人完成，Agent 与自动化不得代替（真车验收同样要求人工操作）。

8.2 权限

表 8-1 权限与自动连接的关系

结论：本需求不新增任何 Android 权限、不新增组件、不改发布流程。若设计阶段发现必须新增权限，按项目约章 §6 走 DECISION-REQUEST。

8.3 数据与隐私

  • D-1 保存什么：首选设备蓝牙地址与名称；连接方式；车机热点 SSID 与口令（既有行为）；最近成功连接时间（本需求新增字段，仅本地）。
  • D-2 存在哪：应用私有 SharedPreferences（diplay、xcertplay_airplay）；allowBackup=false；不进入设置备份白名单；不进诊断；不上传。
  • D-3 保留多久：直到车主忘记设备或清除应用数据；本需求不引入自动过期删除。
  • D-4 谁能读到：仅本应用进程；root/系统级 ADB 可读——这是既有边界，本需求不扩大。
  • D-5 他人能否冒连：接入热点只需 Wi-Fi 口令；进入 CarPlay 仍需完成 iAP2 配对认证（NFR-005）。因此"旁人拿到热点口令"不等于"能投屏"。但开放热点（空口令）会显著降低门槛，必须在 H3 清单中单独检查，且本需求不得自动创建开放热点。
  • D-6 诊断：只记录状态与时间，不记录凭据；导出前人工复核（项目约章 §6 S0）。
S0 红线提示 诊断报告、公开评论、提交内容中不得出现热点口令、配对记录、身份资产或签名文件。设计/开发阶段任何"为调试方便把口令打进日志"的做法一律拒绝。

9.1 恢复原则

  1. 先判断"是否可重试"，再决定是否消耗预算；不可重试的失败一次也不重试。
  2. 任何失败都不得清空首选设备或热点设置（BR-3）。
  3. 失败状态必须可被下一次真实触发（上电、蓝牙到达、打开应用）重新开启新会话。
  4. 连续失败达到预算后，界面必须给出"为什么"和"下一步做什么"，而不是只给错误码。

10.2 复现条件与所需诊断信息

复现自动连接问题所需的最小信息（缺任一项则该问题不可归因）：

  1. 车型与 DiLink 版本、Android API 级别、固件构建号；
  2. iPhone 型号与 iOS 版本；连接方式（MANUAL / WIFI_P2P / EXISTING_WIFI）；
  3. 触发源：冷启动 / 蓝牙到达 / 休眠唤醒 / 手动打开；auto_connect、connect_on_phone_bluetooth、auto_start_on_boot、auto_enable 四个开关的实际状态；
  4. 是否具备 WRITE_SETTINGS、SYSTEM_ALERT_WINDOW、BLUETOOTH_CONNECT；是否配置 ADB；
  5. 车机热点是否开启、SSID 是否与保存值一致（只比对，不上传明文）；
  6. DiPlay 诊断报告（导出后人工复核再外发）：应包含触发源、后端、阶段、attempt 次数、总耗时、失败分类；
  7. 可见症状与最后完成的连接阶段（Home 文案或 CarPlay 启动界面截图，脱敏后）。

不要在公开 issue 中附带：完整网络抓包、热点口令、配对记录、设备备份、身份文件。
