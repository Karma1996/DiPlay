2. 预审范围、输入与方法

2.1 预审了什么

  • 24 条设计断言 DA-001…DA-024：逐条判"可执行 / 需澄清 / 不可执行"，并给出可落地的测试类与假件。
  • 25 条验收标准 AC-001…AC-025：逐条给出验证层级（单测 / Robolectric / 仪器 / 真车 V-0x / 人工）与证据来源；无路径的标缺口。
  • 11 个测试接缝（§14.1 表 14-1）：核对是否足以覆盖 25 AC，是否需要在 build 前补可注入点或假件。
  • "是否新增 androidTest 源集"：只给建议与理由，范围决定权在 H2 人类。

2.2 怎么核的

对每条断言，回到它声称的落点逐文件核对：PhoneBluetoothReceiver.kt、WirelessStartupRetryBudget.kt、DiPlayActivity.kt（AUTOMATIC_CONNECTION 段与诊断入口）、DiagnosticRedactor.kt、CarHotspotOffConnectTest.kt、PhoneBluetoothReceiverTest.kt、ExternalIntentExtrasTest.kt、WirelessStartupRecoveryTest.kt、AdaptiveSettingsUiTest.kt、SettingsTranslationsTest.kt、SettingsLayoutPolicyTest.kt、DiPlayAuthenticationTest.kt、common/build.gradle.kts、.github/workflows/android.yml、common/src/main/res/values*。凡设计引用的行号/类名，均以当前基线复核；不一致的写在 §4.2。

已核实的关键事实
  • 仓库当前没有 androidTest 源集（只有 shared/src/test、common/src/test、samples/home/src/test），CI 也不跑 connected 测试。
  • common 模块已启用 Robolectric 4.17 + unitTests.isIncludeAndroidResources = true，现有测试已能驱动 DiPlayActivity、PhoneBluetoothReceiver、设置页、ShadowAlertDialog；这是本设计"JVM 覆盖交互语义"的现实基础。
  • SettingsSection.AUTOMATIC_CONNECTION 及其卡片基线已存在（DiPlayActivity.kt:119、:1778），设计 §11/FR-011 中"新增该卡片/该段"的表述应收窄为"在既有段内新增总开关与子项"。
  • 11 套 values* 目录各含 230 个 settings_* 键；SettingsTranslationsTest 扫描模块 src/main/res 全部 xml，新键用 settings_auto_connect_* 前缀确实会被 11 语言门禁自动覆盖。
  • common/build.gradle.kts 把单测堆上限设为 2g，并注明"1g 时再加一个 Robolectric 类就会 OOM"——新增 6 个 Robolectric 测试类需要按这条现实做合并（见 G-09）。
  • D-1 的控件移动会破坏两个既有 section 级测试：BydAdbSettingsUiTest（直接调用 renderBydAdbControls 并在其中查找 auto_car_hotspot_title，见 :68/:90）与 CarHotspotSwitchTest（switchFor(auto_car_hotspot_title) 只在 BYD_ADB 渲染结果里找，见 :274-275）。设计 §10.4/§16 R-007 未登记这两个文件，见 G-12。

3. 总体判定

结论：可用（PASS_WITH_ACTIONS）· 无阻塞项 · 可进入 H2

设计语义成立，11 个接缝足以承载 25 条 AC 的 JVM/Robolectric/CI 部分；没有需要退回设计重做的阻塞项。附 2 项须书面澄清（DA-018、DA-019）与 12 项覆盖/契约补充（G-01…G-12），全部可在 build 前以"设计勘误 + 测试设计落项"收口，不改变 FR/NFR/AC 语义，不扩 scope。

7. 是否新增 androidTest 源集（建议）

建议：本需求不新增 androidTest 源集。 用 src/test 的 Robolectric 覆盖可 JVM 证明的交互语义，用 H3 真车覆盖硬件相关项；不把无法在 CI 执行的测试塞进仓库。

7.1 依据（实测）

  • 仓库现状：只有 shared/src/test、common/src/test、samples/home/src/test，没有 androidTest 目录。
  • CI 现状：.github/workflows/android.yml 只跑 :shared/:common/:home 单测、:mobile/:home/:maphost lint、三个 debug APK 构建；没有模拟器、没有 connectedAndroidTest、没有设备农场。
  • 能力现状：common 已开 unitTests.isIncludeAndroidResources = true + Robolectric 4.17；现有测试已能驱动 DiPlayActivity、PhoneBluetoothReceiver、设置页、ShadowAlertDialog、nextStartedActivity。本需求需要的 JVM 交互语义不需要仪器测试。
  • 真车项的不可替代性：蓝牙 ACL 顺序、热点固件、休眠唤醒、倒车影像叠加、认证握手，在模拟器上同样无法证明——即使加了 androidTest，这些仍必须 H3。

7.2 理由

  1. 新增源集会引入一批CI 永远跑不到的测试，违反"不伪造证据、不把未运行标成通过"（S01 协议第 8/9 条）。
  2. 要让它可执行，必须改 CI（加模拟器/设备农场）与模块结构，属于额外范围与时长，H1 的 C-1/A-007 没有授权，应由 H2 作为独立决策，而不是塞进本需求。
  3. Robolectric 已覆盖本设计里所有"可在 JVM 证明"的断言；剩下的是 H3 的职责，不是测试层级的缺口。

7.3 如果将来确实需要

单独提范围决策：指定设备矩阵（API 24/29/33）、CI 模拟器任务与超时预算，并把"仪器测试必须真实运行"作为入口条件；在此之前不建空源集。该建议只作为 H2 参考，范围决定权在人类。
